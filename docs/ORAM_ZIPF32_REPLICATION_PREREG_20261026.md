# Preregistered 32-address Zipf ORAM timing replication

**Status:** registered before collection. The frozen machine-readable
configuration is
[`oram-isolated-zipf32-replication-20261026.json`](../experiments/configs/oram-isolated-zipf32-replication-20261026.json).

## Question and scope

This independent run asks whether the existing, fixed temporal leaf/timing
classifier can infer a hot-versus-cold logical address under a fresh
32-address Zipf workload and a write-heavy operation mix, and whether that
inference is reduced by Path ORAM relative to plaintext and encrypt-only
controls. It tests one declared observer, classifier, geometry, and synthetic
workload. It cannot establish general ORAM security or remote timing behavior.

## Frozen workload and collection

Each of 30 trials has eight disjoint sessions of 256 measured operations on a
32-block, Z=4 store. There are 16 independent warmup accesses before each
measured session. The address distribution is the normalized 32-element
Zipf law `p(i) proportional to (i+1)^(-1.15)`, with addresses 0 through 3
declared hot. The hot class therefore has probability 0.5868 under the
configured IID distribution. Read probability is 0.35; the remaining
operations are writes. Address persistence is zero. The workload seed is
20261032 and the per-trial/session schedules are generated by the existing
reproducible harness.

The same logical address and read/write schedule is captured for plaintext,
encrypt-only, and Path ORAM. Each mode uses its own fresh storage state and
cryptographic randomness. The server-visible ORAM bucket service runs as a
separate process, and the recorded interval is the bucket handler only. The
service is not CPU-pinned; its effective CPU mask and child-process metadata
are retained. This isolates the timing interval from client path computation
and pipe waiting, but it does not isolate the process from shared-host
scheduling or other host activity.

## Attacker, metric, and decision rule

The sole primary metric is the mean of 30 per-trial ROC AUC values for
hot-versus-cold access prediction. Each trial trains and scores on disjoint
sets of four complete sessions; no session contributes to both sets. The
existing `TemporalLeafTimingAttack` is used without tuning: its fixed
128-tree, depth-8 random forest, minimum leaf size 5, balanced class weights,
and random state 1907. It receives the existing observer features only:
visible bucket identifiers, fixed byte counts, handler-only service times,
within-session tag frequencies, recent tag/timing history, and short-window
summaries. Logical addresses and labels remain in private driver traces and
are not supplied to fitting or prediction.

The 95% interval is the percentile bootstrap over 30 whole-trial AUC values
using 5,000 resamples. Accuracy and profile-majority accuracy are descriptive
only. Plaintext and encrypt-only controls are evaluated first. Both must have
mean AUC at least 0.80 and a lower interval bound above 0.50. If either fails,
the run is inconclusive and Path ORAM is not scored as a defense. If both pass,
Path ORAM is evaluated once. No workload, classifier, feature, threshold, or
metric changes are permitted after inspecting the result.

An ORAM interval whose lower bound exceeds 0.50 is evidence of inference for
this attack and setup. An interval containing 0.50 is only a failure to resolve
the signal at this experiment's power; it is not a proof of
indistinguishability.

## Retained evidence

The run must preserve its exact configuration, all raw observer and private
driver traces, per-trial predictions, report, figure, process/PID/CPU-mask
metadata, source and binary hashes, host observation, tool versions, runtime,
and hashes of every raw file. An independent audit must verify every hash,
address bound, operation count, paired schedule, session split, positive
control decision, and primary metric before interpreting the result.

The run command is:

```sh
cargo build --locked --release -p oblivion-store \
  --example oram-measure --example oram-control
.venv/bin/python -m research.analysis.oram_isolated_replication \
  --config experiments/configs/oram-isolated-zipf32-replication-20261026.json \
  --output experiments/results/oram-isolated-zipf32-replication-20261026 \
  --oram-binary target/release/examples/oram-measure \
  --control-binary target/release/examples/oram-control
```
